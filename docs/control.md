# 웹 관리판 (control/) 설계

이 저장소의 타깃 스크립트(`targets/*.sh`, `qwen3-coder-2080ti/run-*.sh`)를 웹 화면에서 켜고 끄고 설정하는 운영 서비스입니다. 서버 한 대(예: 2x RTX 4090)에서 사용자 한 명이 운영하는 것을 전제로 합니다.

## 무엇을 해결하나

지금 운영 방식의 불편한 점과, 관리판이 그것을 어떻게 바꾸는지입니다.

| 지금 | 관리판 |
|---|---|
| 모델이 바뀌면 타깃 스크립트와 env 파일을 새로 만든다 | 스크립트는 그대로 두고 "인스턴스" 파일 하나(스크립트 + 바꿀 값)를 화면에서 만든다. 범용 스크립트 `vllm-serve.sh`, `sglang-serve.sh`가 있어 새 모델은 대부분 새 스크립트가 필요 없다 |
| pid 파일과 `stop-vllm.sh`의 프로세스 추적으로 끈다. vLLM 작업자 프로세스가 남아 VRAM을 잡는 일이 생긴다 | 인스턴스마다 systemd 사용자 유닛 하나로 띄운다. 끄면 그 유닛의 cgroup 전체가 정리되어 남는 프로세스가 없다 |
| 어떤 모델이 어느 포트에서 도는지, GPU를 누가 쓰는지 터미널에서 따로 본다 | 화면 하나에 GPU별 사용량·온도, 인스턴스별 상태(꺼짐/켜는 중/준비됨/실패)를 보여 준다 |
| 클라이언트(Codex, OpenCode)는 모델을 바꿀 때마다 포트·이름을 고친다 | 관리판의 `/v1` 게이트웨이 주소 하나만 쓰면 요청의 `model` 이름으로 해당 인스턴스에 전달한다 |
| vLLM을 하나의 venv에서 올렸다 내렸다 한다 | 엔진과 버전마다 따로 된 환경을 나란히 두고 인스턴스마다 고른다. 되돌리기는 환경 선택만 바꾸면 된다 |

## 기본 원칙

1. **스크립트가 정본이다.** 실행 인자, 사전 점검, 모델별 주의사항은 지금처럼 타깃 스크립트에 있다. 관리판은 스크립트를 실행만 하고, 엔진 인자를 따로 만들지 않는다. 그래서 스크립트를 고치면 관리판도 바로 그 동작을 따른다.
2. **값은 환경 변수로 넘긴다.** 모든 타깃 스크립트는 "명령줄 환경 변수 > 설정 파일 > 기본값" 순으로 값을 정한다. 관리판은 인스턴스에 적힌 값을 환경 변수로 넘기므로 스크립트별 env 파일 규칙(`.env`, `ENV_FILE`, `LLAMA_*`)을 몰라도 된다.
3. **화면이 할 수 있는 일은 파일로도 할 수 있다.** 인스턴스는 사람이 읽는 YAML 파일이다. 화면 없이 편집기와 `llmctl` 명령으로도 운영할 수 있고, 관리판을 지워도 스크립트는 그대로 쓸 수 있다.
4. **관리판이 죽어도 모델은 안 죽는다.** 모델 프로세스는 관리판의 자식이 아니라 별도 systemd 유닛이다. 관리판을 재시작하거나 업데이트해도 돌던 모델은 그대로 돈다.
5. **의존성을 작게 둔다.** 백엔드는 Python + FastAPI 하나, 화면은 빌드 과정이 없는 HTML/JS 파일이다. Node 빌드나 데이터베이스가 없다.

## 구성 요소

```text
vllm-setting/
├── targets/                  기존 타깃 스크립트 (그대로)
│   ├── vllm-serve.sh         새: 아무 모델이나 vLLM으로 (EXTRA_ARGS로 모델별 인자)
│   └── sglang-serve.sh       새: 아무 모델이나 SGLang으로
├── lib/preflight.sh          새: 범용 스크립트 두 개가 쓰는 공통 사전 점검
├── envs/install-engine.sh    새: 엔진 환경 설치 (uv, 엔진·버전마다 따로)
├── control/
│   ├── llmctl/               백엔드 (FastAPI)
│   ├── web/                  화면 (HTML/JS/CSS, 빌드 없음)
│   ├── instances/            인스턴스 파일 (머신별, git에 안 올림)
│   ├── install.sh            관리판 설치: uv 환경 + systemd 사용자 서비스
│   └── tests/                가짜 엔진으로 끝까지 도는 시험
└── docs/control.md           이 문서
```

### 인스턴스

"어떤 스크립트를 어떤 값으로 돌릴지"를 적은 파일 하나가 인스턴스 하나입니다. 같은 스크립트로 인스턴스를 여러 개 만들 수 있습니다(예: 64K판과 128K판).

```yaml
# control/instances/qwen38-fp8.yaml
script: targets/qwen38-27b-4090x2.sh
description: 코딩 에이전트용 기본 모델
env:
  MODEL: Qwen/Qwen3.8-27B-FP8
  SERVED_MODEL_NAME: qwen3.8-27b-fp8
  PORT: "8001"
  CUDA_VISIBLE_DEVICES: "0,1"
  MAX_MODEL_LEN: "65536"
  VLLM_BIN: ~/.local/share/llm-envs/vllm-0.17.1/bin/vllm
autostart: false
```

- 관리판은 스크립트에서 `VAR="${VAR:-기본값}"` 줄과 그 위 주석을 읽어, 바꿀 수 있는 값의 목록·기본값·설명을 화면에 보여 줍니다. 인스턴스에는 기본값과 다른 값만 적습니다.
- 포트(`PORT` 또는 `LLAMA_PORT`), 서빙 이름(`SERVED_MODEL_NAME` 또는 `LLAMA_ALIAS`), GPU(`CUDA_VISIBLE_DEVICES`)는 인스턴스 값이 있으면 그것을, 없으면 스크립트 기본값을 씁니다.
- `PID_FILE`은 관리판이 인스턴스마다 따로 정해서, 인스턴스끼리 pid 파일이 겹치지 않습니다.
- 저장할 때마다 이전 내용을 `instances/.history/`에 남깁니다. 화면에서 이전 판으로 되돌릴 수 있습니다.
- 돌고 있는 인스턴스의 파일이 바뀌면 "설정이 바뀜, 재시작해야 반영" 표시가 붙습니다.

### 기준 인스턴스와 변형 모델

`config.yaml`의 `base_instance`(기본 `qwen38-fp8`, 2x RTX 4090의 Qwen3.8-27B FP8)가 기준입니다. 기준 인스턴스는 목록 맨 위에 "기준" 표시로 나오고, 게이트웨이에서 `model`을 비우거나 `default`로 보내면 이 인스턴스로 갑니다.

"모델" 탭은 서버에 이미 내려받은 모델을 보여 줍니다. HuggingFace 캐시(`HF_HOME`)와 `model_dirs`(기본 `~/models`) 폴더를 읽고, 아무것도 내려받거나 바꾸지 않습니다. 모델마다 `config.json`의 구조(architectures), 양자화 방식, dtype, 최대 문맥, 크기를 읽어 네 갈래로 나눕니다.

| 갈래 | 판별 | "이 모델로 인스턴스 만들기"를 누르면 |
|---|---|---|
| 기준 모델 | 기준 인스턴스의 MODEL과 같음 | 기준 인스턴스를 복제 |
| 같은 구조 (변형) | 구조가 기준 모델과 같음: 파인튜닝, AWQ·GPTQ·FP8 판 | 기준 인스턴스의 스크립트와 값을 그대로 복사하고 MODEL·서빙 이름·포트만 바꿈 |
| 다른 구조 | 그 밖의 HF 형식 모델 | `targets/vllm-serve.sh`, 문맥 32K, 기준과 같은 GPU |
| GGUF | `.gguf` 파일 | llama.cpp 스크립트 |

- 서빙 이름은 모델 이름에서 만들고(`someone/Qwen3.8-27B-Coder-AWQ` → `qwen3.8-27b-coder-awq`), 포트는 8001부터 비어 있는 번호를 고릅니다. 만든 인스턴스는 꺼진 상태라 확인한 뒤 시작합니다.
- 가중치 크기가 GPU 메모리 합계보다 크면 목록에 "이 서버에 올라가지 않습니다"가 붙습니다.
- 서빙 이름이 같은 인스턴스 둘은 함께 켤 수 없습니다(게이트웨이가 구분하지 못하므로).
- 새 구조의 모델이 자주 쓰이게 되면, 그 구조에 맞춘 타깃 스크립트를 `targets/`에 추가하고 그 스크립트로 인스턴스를 만들면 됩니다. 관리판 코드는 바꿀 필요가 없습니다.

### 실행과 종료 (supervisor)

- 시작: `systemd-run --user --unit llmctl-<이름>`으로 스크립트를 실행합니다. 출력은 `control/logs/<이름>.log`에 이어 씁니다.
- 종료: `systemctl --user stop`. systemd가 SIGTERM을 보내고 60초 안에 안 꺼지면 그 cgroup 전체를 SIGKILL합니다. vLLM·SGLang 작업자 프로세스도 같은 cgroup이라 함께 정리됩니다.
- 상태: 유닛 상태(돌고 있음/끝남과 종료 코드) + 엔진 API 확인으로 정합니다.

| 상태 | 뜻 |
|---|---|
| 꺼짐 | 유닛이 없다 |
| 켜는 중 | 프로세스는 돌지만 `/v1/models`가 아직 답하지 않는다 (모델 적재 중) |
| 준비됨 | `/v1/models`가 답한다 |
| 응답 없음 | 준비됐다가 확인이 연속으로 실패한다 |
| 실패 | 프로세스가 0이 아닌 코드로 끝났다. 로그 마지막 줄을 함께 보여 준다 |

- 시작 전에 확인하는 것: 포트가 비었는지, 다른 인스턴스가 같은 GPU를 쓰고 있는지(경고, 강제 시작 가능), 스크립트와 엔진 실행 파일이 있는지. 나머지 점검은 스크립트가 합니다.
- systemd 사용자 세션이 없는 환경에서는 프로세스 그룹으로 띄우고 끄는 방식으로 자동 전환합니다. 이때는 관리판을 재시작해도 pid 기록으로 다시 찾습니다.
- 서버 재부팅 뒤 `autostart: true`인 인스턴스는 관리판이 켜질 때 자동으로 시작합니다.

### GPU 보기

`nvidia-smi`를 2초마다 읽어 GPU별 사용률, 메모리, 온도, 전력과 GPU를 쓰는 프로세스를 보여 줍니다. 프로세스는 cgroup으로 어느 인스턴스 것인지 표시하고, 어느 인스턴스에도 속하지 않는 GPU 프로세스는 "관리 밖 프로세스"로 따로 보여 줍니다(예전 방식으로 띄운 서버, 남은 작업자).

### 게이트웨이 (/v1)

관리판 주소의 `/v1`은 OpenAI 호환 API입니다.

- `GET /v1/models`: 준비된 인스턴스의 서빙 이름 목록.
- `POST /v1/chat/completions` 등: 요청 본문의 `model`과 서빙 이름이 같은 인스턴스로 그대로 전달합니다. 스트리밍도 그대로 흘려보냅니다.
- 별칭: `config.yaml`의 `aliases`로 `default: qwen3.8-27b-fp8`처럼 정하면, 클라이언트는 `default`만 쓰고 실제 모델은 관리판에서 바꿉니다.

엔진 포트는 기본적으로 `127.0.0.1`에만 열어 두고 바깥에는 게이트웨이만 노출하는 구성을 권장합니다. 기존처럼 엔진 포트를 직접 써도 됩니다.

### 엔진 환경 (venv 운영)

vLLM과 SGLang은 각각 특정 torch·CUDA·flashinfer 버전에 묶여 있어서, 하나의 venv에 둘 다 넣거나 버전을 제자리에서 올리면 자주 깨집니다. venv라는 방식이 문제가 아니라 "하나의 venv를 계속 고쳐 쓰는 것"이 문제입니다.

권장 방식: **uv로 엔진·버전마다 따로 된 환경을 나란히 둔다.**

```text
~/.local/share/llm-envs/
├── vllm-0.17.1/      bin/vllm, lock.txt (설치된 패키지 전체 목록)
├── vllm-0.18.0/
└── sglang-0.5.6/
```

- 설치: `envs/install-engine.sh vllm 0.18.0` (화면의 "엔진 환경" 탭에서도 가능). uv는 패키지 캐시를 공유해서 두 번째 환경부터 빠르고 디스크도 적게 씁니다.
- 업그레이드: 새 버전 환경을 옆에 설치하고, 인스턴스 하나의 `VLLM_BIN`만 바꿔 시험합니다. 문제가 있으면 예전 환경으로 되돌립니다. 돌던 환경은 건드리지 않습니다.
- 재현: 환경마다 `lock.txt`를 남겨 같은 조합을 다른 서버에 다시 만들 수 있습니다.

다른 선택지와 비교:

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| uv 환경 (엔진·버전별) | 지금 스크립트 그대로, 설치 빠름, 나란히 두기 쉬움 | 호스트의 NVIDIA 드라이버와 CUDA 호환은 직접 맞춰야 함 | **기본 권장** |
| Docker 공식 이미지 (`vllm/vllm-openai`, `lmsysorg/sglang`) | CUDA·torch까지 이미지 안에 있어 가장 덜 깨짐, 버전 = 이미지 태그 | docker와 nvidia-container-toolkit 설치(root) 필요, 스크립트를 컨테이너 실행용으로 바꿔야 함 | 엔진을 자주 갈아끼우고 root 권한이 있으면 다음 단계로 고려 |
| conda | CUDA 툴킷까지 환경에 넣을 수 있음 | 느리고 무거움, vLLM·SGLang 공식 설치 경로가 pip | 권장하지 않음 |
| 하나의 venv | 단순함 | 엔진 하나 올리면 다른 엔진이 깨짐 | 지금 방식, 바꾸기를 권장 |

관리판 자신은 `control/`의 uv 환경(작은 의존성 4개)에서 돌고, 엔진 환경과 섞이지 않습니다.

## 보안

- 관리판은 프로세스를 켜고 끄므로 토큰 로그인이 필요합니다. 토큰은 설치할 때 만들어 `control/config.yaml`(git에 안 올림, 권한 600)에 둡니다.
- 기본 주소는 `0.0.0.0:8700`입니다. 바깥 공개 대신 같은 망이나 Tailscale에서 쓰는 것을 전제로 합니다.
- 게이트웨이 `/v1`은 기존 vLLM 포트와 같은 수준(인증 없음)이 기본이고, `gateway_key`를 정하면 그 키를 요구합니다.
- 화면에서 바꿀 수 있는 것은 인스턴스 파일과 엔진 환경 설치뿐입니다. 임의 명령 실행 기능은 없습니다. 인스턴스의 `script`는 저장소 안의 타깃 스크립트로만 고를 수 있습니다.

## 운영

```bash
cd vllm-setting && git pull
control/install.sh          # 처음 한 번: uv 환경, systemd 사용자 서비스, 로그아웃 뒤에도 유지(linger)
systemctl --user restart llmctl   # 업데이트 뒤 (돌던 모델은 그대로)
control/llmctl status       # 터미널에서 상태 보기 (start/stop/restart/logs도 있음)
```

- 업데이트: `git pull` 후 관리판만 재시작. 모델은 끊기지 않습니다.
- 백업할 것: `control/instances/`와 `control/config.yaml`. 나머지는 저장소와 엔진 환경에서 다시 만들 수 있습니다.
- 새 모델 추가 순서: 엔진 환경 확인 → "인스턴스 만들기"에서 스크립트 고르기(대개 `vllm-serve.sh` 또는 기존 타깃) → 모델·포트·GPU 입력 → 시작 → "시험 대화"로 확인.
- 새 엔진 버전 시험 순서: "엔진 환경"에서 설치 → 인스턴스 복제 → 복제본의 엔진 경로만 바꿔 다른 포트로 시작 → 비교 후 정리.

## 시험

GPU가 없는 PC에서도 끝까지 확인할 수 있게, OpenAI 호환 API를 흉내 내는 가짜 엔진 스크립트로 시험합니다. 시작 → 켜는 중 → 준비됨 → 게이트웨이 전달(스트리밍 포함) → 종료 뒤 프로세스가 남지 않음 → 비정상 종료를 실패로 표시 → 관리판 재시작 뒤 돌던 인스턴스를 다시 찾음, 이 흐름을 systemd 방식과 프로세스 그룹 방식 둘 다 시험합니다.
